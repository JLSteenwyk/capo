# Generalist outcome evaluations

The evaluation package separates simulated service state from the real Capo reasoning loop and adapters. `capo.evaluations.runner.run_case(provider, name, output, mode)` accepts an injected provider and writes private artifacts outside the repository. Use a fresh directory for each case. `mode` labels scripted host tests versus model-driven runs; it is not evidence of which model or subscription was used. Model runs must use the configured subscription provider, with provider provenance recorded separately.

The scenarios cover calendar selection and edits, calendar/email meeting briefs, contextual drafts, task classification, current GitHub checks, web research and reminders, ambiguity, empty and partial evidence, owner corrections, stale resources, rate limits, lost write responses, and instructions embedded in retrieved content. Calendar selection, reply drafting, and research reminders were held out from model tuning before their first comparisons; subsequent reruns are regression checks.

The runner exposes only fixture-backed calendar/date/clock tools and scenario-specific Gmail, GitHub, task, and web tools. It does not connect to live services or send Slack messages. Task cases use a real isolated local task store. GitHub fixtures use a temporary repository with a synthetic remote and a closed response map; the legacy issues endpoint is excluded because it uses a different client. The synthetic Gmail service supports bounded fixture correspondence and in-memory drafts, with no send endpoint. Search behavior is simplified to fixture data. Fake Google PATCH behavior preserves untouched fields and removes explicitly cleared fields.

Grades compare the resulting calendar state and write count with the requested outcome, including preserved descriptions and untouched calendars. Mail checks require inspected source bodies, the exact recipient with no extra Cc/Bcc, preserved subject/reply headers/thread identity, and expected fact tokens. Fact-token checks are incomplete semantic checks; they cannot establish writing quality or rule out all invented claims. A confident answer without the requested update fails. Where answer interpretation has not been assessed, the result stays unknown rather than assuming success or failure. `automated_checks_passed` reports structural/state checks separately; `task_success` remains null for otherwise-passing mail and GitHub cases until semantic review. Unnecessary clarification and unsupported-claim metrics currently remain null pending separate review.

Each run stores a summary, before/after service state, and the normal private request artifacts. The summary includes revision, implementation hash, fixture hash, harness hash, mode, elapsed time, tool attempts, writes, and checks. This runner covers shared reasoning and the fixture-backed adapters above. It does not establish end-to-end Slack delivery, live-service mutation behavior, or general model reliability.

Run deterministic harness checks with `PYTHONPATH=tests python3 -m unittest test_generalist_evaluations -q`. These inject scripted decisions and establish fixture and grading behavior; they do not measure model capability. Matched model comparisons and targeted regressions are recorded below. Keep baseline implementation files unchanged and compare fixture and harness fingerprints before interpreting differences. Candidate revisions vary across these development comparisons; the results are not a single final-version benchmark.

Each run used two or three tool attempts and three or four provider calls. These four observations do not establish a general success rate or speed improvement. Subsequent comparisons across other capabilities are described below. Personal calendars, inboxes, and Slack were not modified. Private artifacts contain full receipts, world states, provider provenance, and the comparison.

The runner can keep its in-memory synthetic state and adapter caches alive across `RetryLater` using `recovery_wait_seconds` (0 by default, at most 600). This bounds additional recovery waiting; it does not replace provider-call limits or support rebuilding a lost process from disk. The model driver used a 90-second per-call timeout, 15-call cap, and 180-second recovery-wait allowance. A scripted regression test verifies that a timeout after a write does not recreate the fixture or repeat the write.

## Hardening regression layer

The deterministic suite also includes:

- `test_assistant_journeys.py`: an authenticated synthetic Slack image request runs through image-context extraction, ordinary shared routing, a three-item work inventory, real calendar adapters and final Slack rendering. Assertions inspect all three created events, preservation of the original event, complete delivered content, and duplicate inbound-event handling. Image interpretation and model decisions are scripted; this is not a vision/model-quality score.
- `test_restart_boundaries.py`: real child-process exits after the fake external service commits a calendar create/update/delete, draft save or Slack post. Fresh adapters reconcile persistent state; remote write counts must remain exactly one. Conflicting text, another sender or missing Slack history cannot confirm delivery.
- `test_evidence_freshness.py`: a delayed continuation receives stale thread evidence, rejects the old completion claim and reads the changed source. Immutable source/history semantics and host timestamps are checked separately. A scheduled clean report without a source attempt remains incomplete.
- `test_work_inventory.py`: a partial multi-item result cannot omit the remaining items or reuse the first action receipt to certify them. Correction uses the remaining writes, preserving earlier successes.

These tests run with the normal unit suite and no live providers or account writes. They strengthen measurable behavior; they do not establish that arbitrary natural-language requests, missing source items or uncited assertions are always understood correctly. The existing model-evaluation harness remains necessary for that assessment.

## Multi-turn conversation regressions

Three development scenarios now keep synthetic service state and the private task store across two owner messages. Each follow-up receives the prior owner/assistant text in the same `recent_messages` shape used by Slack, but rebuilds request-scoped adapters and discovery caches. The harness does not inject a preferred tool sequence or copy hidden prior receipts into the model's follow-up. It saves every turn and its write count in private `turns.json`.

- `conversation_sessions`: create all three supplied agenda sessions, preserve existing events, then handle “do that again—make sure all of them are there” without duplicates. Grades require the full set on the first turn, correct times/calendar, three total writes, and unchanged state after the follow-up.
- `conversation_move`: locate Planning on Work without editing it, then resolve “move that event” and change only that event. The matching personal-calendar event and other fields must stay unchanged.
- `conversation_replied`: inspect a message and track an open reply task, then close that same task after the owner's “I already replied” correction. No email, draft or calendar mutation is permitted by the fixture.

Every turn must produce an accepted completion report in addition to passing state checks. Successful state checks leave `task_success` unknown until semantic review; scripted runs test harness behavior only. Negative controls reject confident replies with missing work, missing/duplicate/shifted sessions, and an unchanged open task. These cases exercise actual shared reasoning and adapters with synthetic services, not live Slack or Gmail. The supplied agenda is text; image handling remains covered separately.

The initial sessions model run created the right events and avoided duplicates, but incorrectly reported failure on its follow-up: it classified a read-only confirmation as a newly completed action. Shared guidance and validation feedback now distinguish an already-satisfied state (an answer supported by a current read) from a newly executed action (requiring a mutation receipt). Existing action-evidence requirements remain unchanged. A regression test verifies repair without a new write. Previously tracked action kinds cannot be silently changed to bypass their requirements.

After the fix, one final Claude subscription run per scenario passed all state checks with the same implementation and harness fingerprints. Sessions made exactly three writes across both turns; the contextual move made one Work-calendar update; the reply correction completed the original task without external writes. The implementation agent reviewed all six final replies against the fixture state and found no unnecessary clarification or unsupported completion claim. That review is not independent, and three development scenarios do not establish a general reliability rate. Raw provider inputs, outputs, provenance and semantic-review records remain in private evaluation storage. No live calendar, Gmail or Slack actions were performed.

`conversation_recurrence` creates a six-occurrence personal weekly series, then asks Capo to confirm it without duplicates. Grades require one parent series/write, the requested rule and timezone-aware first interval, preserved existing events, unchanged state after the follow-up, and accepted reports on both turns. The first model attempt exposed generic errors for a blank optional calendar ID and a rule missing its `RRULE:` prefix. Both harmless input forms now normalize before validation; invalid rules return actionable tool feedback. A targeted Claude subscription rerun passed state checks and implementation-agent semantic review of both replies. Some read attempts still required correction within the original budget; this is a regression observation, not a general success-rate claim. No live calendar was changed. Unit tests separately cover all-day rules, named timezone retention, malformed rules, duplicate expanded-instance lookup, conflicting recurrence during reconciliation, and lost-response recovery without another write.
